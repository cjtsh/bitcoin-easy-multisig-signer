# Bitcoin Easier Signer — code audit

**Audit target:** `cjtsh/bitcoin-easy-multisig-signer`, `phase2-transaction-builder` at [`e5e47a1`](https://github.com/cjtsh/bitcoin-easy-multisig-signer/commit/e5e47a135fda09c8c91a87abccfd4d06b4941820), including the published v0.1.27 code at `b698ed0`. Audited 29 September 2026. The default `main` branch is older and does not contain the completed signing flow. I read the README, roadmap, handoff, history, disclaimer, source, tests, build scripts, and workflow, and checked the relevant [BSMS specification](https://bips.dev/129/), [PSBT specification](https://bips.dev/174/), and [HWI project](https://github.com/bitcoin-core/HWI). I ran the 135-test suite (pass; 8 platform-dependent skips) and an additional malformed-signature probe. I did **not** inspect the owner's wallet, run a physical signer, validate a downloaded DMG, or make a mainnet transaction. The handoff records two confirmed Testnet4 sends with three device models; I treat that as project evidence, not as a test I repeated.

**Assessment:** This is a credible, thoughtfully guarded Testnet4 prototype. It is **not yet ready to authorize a mainnet broadcast**. The highest-value fixes concern proof that change belongs to the actual wallet, verification and binding of the signed result, and an accurate final review screen. Passing Testnet4 sends prove an important path works; they do not prove every supported BSMS export or a mainnet send is safe.

## 1. Safety of operation

### Findings

- **Hot — Change ownership is assumed for receive-only exports.** [`wallet_layout`](https://github.com/cjtsh/bitcoin-easy-multisig-signer/blob/e5e47a135fda09c8c91a87abccfd4d06b4941820/wallet_service.py#L176-L224) converts `/0/*` or `/*` into `/1/*`, and [`wallet_summary`](https://github.com/cjtsh/bitcoin-easy-multisig-signer/blob/e5e47a135fda09c8c91a87abccfd4d06b4941820/wallet_service.py#L262-L309) then allows preparation. The reference address proves the receiving path only. Scanning a newly derived change branch and finding no history does not establish that the wallet or recovery software recognizes that branch. For the tested Sparrow wallet it worked; for an arbitrary imported wallet, a partial send could place most of the funds at a change output the intended wallet cannot readily recover. BIP129 treats path restrictions and signer confirmation as part of multisig setup; see its [descriptor record and signer checks](https://bips.dev/129/).
- **Hot — Final review does not display the final destination or change address.** The backend returns destination, amount, fee and change *amount* in [`_finalize`](https://github.com/cjtsh/bitcoin-easy-multisig-signer/blob/e5e47a135fda09c8c91a87abccfd4d06b4941820/gui.py#L504-L524), but [`showFinal`](https://github.com/cjtsh/bitcoin-easy-multisig-signer/blob/e5e47a135fda09c8c91a87abccfd4d06b4941820/ui.html#L1192-L1205) renders only amount, fee, size, signers and txid. The [final checkbox](https://github.com/cjtsh/bitcoin-easy-multisig-signer/blob/e5e47a135fda09c8c91a87abccfd4d06b4941820/ui.html#L408-L423) says the user checked the destination “above,” although it is absent from that final panel. The earlier review contains it, but the last irreversible decision should display every output, including change.
- **Warm — Finalization counts signatures without validating them.** [`is_complete` and `finalize_multisig`](https://github.com/cjtsh/bitcoin-easy-multisig-signer/blob/e5e47a135fda09c8c91a87abccfd4d06b4941820/signing.py#L102-L195) check that entries exist for expected public keys, then assemble witness data; they do not verify DER encoding, sighash type, or ECDSA signatures against the transaction and input values. I corrupted signatures in a synthetic, otherwise valid PSBT: `is_complete` returned true and `finalize_multisig` returned a raw transaction. A Bitcoin node should reject such a transaction, so this finding is primarily a false-success/failed-payment risk, not demonstrated theft. The [`test_signing.py` test](https://github.com/cjtsh/bitcoin-easy-multisig-signer/blob/e5e47a135fda09c8c91a87abccfd4d06b4941820/tests/test_signing.py#L48-L94) independently verifies *valid test signatures after* finalization; it does not prove the finalizer rejects invalid ones.
- **Warm — Signed PSBT metadata and final review are insufficiently bound to the prepared result.** [`_sign`](https://github.com/cjtsh/bitcoin-easy-multisig-signer/blob/e5e47a135fda09c8c91a87abccfd4d06b4941820/gui.py#L468-L501) accepts an HWI-returned PSBT if its transaction ID matches. It does not compare the input UTXOs, scripts, derivations, sighash fields, or output metadata to the prepared PSBT. [`finalize_multisig`](https://github.com/cjtsh/bitcoin-easy-multisig-signer/blob/e5e47a135fda09c8c91a87abccfd4d06b4941820/signing.py#L181-L195) calculates the displayed final fee from mutable PSBT `witness_utxo` values. The txid check does lock the transaction's non-witness inputs and outputs, which is a meaningful safeguard; it does not authenticate the fee metadata or prove the finalized witness is spendable.
- **Warm — Explorer observations can be stale or manipulated.** The scanner trusts Esplora for address totals, status and UTXO lists, then verifies selected previous transactions against their txid, value and derived script ([scan](https://github.com/cjtsh/bitcoin-easy-multisig-signer/blob/e5e47a135fda09c8c91a87abccfd4d06b4941820/wallet_service.py#L371-L454), [builder](https://github.com/cjtsh/bitcoin-easy-multisig-signer/blob/e5e47a135fda09c8c91a87abccfd4d06b4941820/wallet_service.py#L694-L722)). Those checks prevent a server from inventing a spendable output without a matching historical transaction, but they cannot prove an output remains unspent, that the server reported all outputs, or that an unconfirmed spend is represented accurately. A 20-address gap and 100-index cap make “send all” mean all *found by this scan*, as the UI partly explains.
- **Nice to have — Fee policy limits liveness.** Preparation requires a live mempool.space quote, refuses a standard quote above 25 sat/vB, and caps the estimated absolute fee at 10,000 sats ([`_prepare`](https://github.com/cjtsh/bitcoin-easy-multisig-signer/blob/e5e47a135fda09c8c91a87abccfd4d06b4941820/gui.py#L644-L695), [builder](https://github.com/cjtsh/bitcoin-easy-multisig-signer/blob/e5e47a135fda09c8c91a87abccfd4d06b4941820/wallet_service.py#L632-L657)). This prevents extreme fee mistakes but can make urgent recovery impossible during congestion or a quote outage. Transactions signal replaceability, yet the app has no fee-bump flow.

### Recommendations to fix

- **Hot:** Require an explicit receive/change descriptor or a verified wallet-policy export for mainnet partial sends. If an inferred branch is retained for a narrowly supported wallet, independently derive its change address in the originating wallet and verify each device recognizes it as change before accepting that wallet; fail closed when this cannot be shown.
- **Hot:** Show network, complete destination, recipient amount, each change address and amount, exact absolute fee, effective final sat/vB, and txid together on the final confirmation screen. Make the final checkbox match what is actually visible.
- **Warm:** Make the finalizer verify every signature, sighash type, input witness script and prevout against the immutable prepared PSBT; ideally run Bitcoin Core `testmempoolaccept` against a trusted node before presenting broadcast as ready. Reject a signer response that changes anything except valid new partial signatures. Recompute the fee from immutable, verified previous outputs and compare it with the reviewed fee.
- **Warm:** Treat explorer data as observations. Before a mainnet broadcast, confirm selected outpoints against an independent node or second backend, check they remain unspent, and make stale/unknown status visible. Keep the current scan-limit wording.
- **Nice to have:** Add a controlled high-fee override backed by a fresh, explicit fee review and an RBF replacement workflow, with tests for congested mempools and many-input transactions.

## 2. Safety of code and keys

### Findings

- **Hot — Build provenance does not yet support high-value distribution.** HWI, embit, pywebview and the rest are appropriate off-the-shelf components, but [`requirements-desktop.txt`](https://github.com/cjtsh/bitcoin-easy-multisig-signer/blob/e5e47a135fda09c8c91a87abccfd4d06b4941820/requirements-desktop.txt) pins only direct dependencies and has no dependency hashes. [`build-macos.sh`](https://github.com/cjtsh/bitcoin-easy-multisig-signer/blob/e5e47a135fda09c8c91a87abccfd4d06b4941820/scripts/build-macos.sh#L70-L101) warns but continues if `LIBUSB_SHA256` is unset; the repository currently has no such Actions variable. The [workflow](https://github.com/cjtsh/bitcoin-easy-multisig-signer/blob/e5e47a135fda09c8c91a87abccfd4d06b4941820/.github/workflows/build-candidate.yml) can still publish that build. The v0.1.27 DMG is ad-hoc signed and unnotarized. A compromised build dependency or distribution channel can defeat all application-level key safeguards.
- **Warm — No app path asks for a seed or private key.** [`probe.py`](https://github.com/cjtsh/bitcoin-easy-multisig-signer/blob/e5e47a135fda09c8c91a87abccfd4d06b4941820/probe.py#L231-L273) sends a PSBT to HWI through a subprocess; HWI asks the device to sign. The app never receives a secret key. This is a strong boundary, but it is conditional on authentic device firmware, trusted HWI/dependencies, and checking what the device actually displays. “Keys stay on hardware” is not a guarantee that a malicious host cannot induce approval of an unintended transaction.
- **Warm — Public wallet data is sensitive.** Explorer requests disclose derived addresses and transaction IDs, and the PSBT passed as an HWI command-line argument contains xpubs, origins, addresses and spending details ([builder](https://github.com/cjtsh/bitcoin-easy-multisig-signer/blob/e5e47a135fda09c8c91a87abccfd4d06b4941820/wallet_service.py#L686-L720), [HWI invocation](https://github.com/cjtsh/bitcoin-easy-multisig-signer/blob/e5e47a135fda09c8c91a87abccfd4d06b4941820/probe.py#L231-L273)). Same-user processes and the selected explorer can observe or correlate some of this. The app uses a local token, loopback bind, Host/Origin checks, no request logging, TLS verification and redirect refusal, which materially reduce exposure ([local API](https://github.com/cjtsh/bitcoin-easy-multisig-signer/blob/e5e47a135fda09c8c91a87abccfd4d06b4941820/gui.py#L225-L355), [HTTP client](https://github.com/cjtsh/bitcoin-easy-multisig-signer/blob/e5e47a135fda09c8c91a87abccfd4d06b4941820/safe_http.py)).
- **Nice to have — A signed, unbroadcast mainnet transaction is itself spend authority.** Phase 5's proposed dry run correctly acknowledges this in [`PHASE-HANDOFF.md`](https://github.com/cjtsh/bitcoin-easy-multisig-signer/blob/e5e47a135fda09c8c91a87abccfd4d06b4941820/PHASE-HANDOFF.md#L132-L153). The current API retains signed PSBT bytes in process memory after signing; a host compromise could broadcast them even though this app's mainnet endpoint refuses broadcast.

### Recommendations to fix

- **Hot:** Build from a reviewed lockfile with hashes for the full dependency tree, make the `libusb` digest mandatory in release CI, generate an SBOM/build provenance record, and verify the exact release artifact. Complete Developer ID signing and notarization before offering the app to other holders of real funds. A checksum published beside an unsigned artifact helps detect transfer errors but is not independent proof of publisher identity.
- **Warm:** Keep HWI as the signing boundary, but document the supported models/firmware and require full on-device review of external destination, amount, fee and change policy. Minimize command-line PSBT exposure if HWI offers a safe stdin or file-descriptor interface. Consider a user-run local node or privacy-aware backend for mainnet scanning.
- **Nice to have:** In the mainnet dry run, use a tiny self-owned destination and a short-lived, isolated session. Do not save or share the signed PSBT or raw transaction; clear it from app state when the rehearsal ends. This reduces exposure, though Python cannot guarantee secure erasure of process memory.

## 3. Efficiency of design

### Findings

- **Hot — The public product story conflicts with the software.** The top of the [README](https://github.com/cjtsh/bitcoin-easy-multisig-signer/blob/e5e47a135fda09c8c91a87abccfd4d06b4941820/README.md#L1-L45) says signing and Testnet4 broadcast work, then says this build does not sign or broadcast. The [review instructions](https://github.com/cjtsh/bitcoin-easy-multisig-signer/blob/e5e47a135fda09c8c91a87abccfd4d06b4941820/ui.html#L367-L397) still tell the user to open the PSBT in another wallet and say the app cannot sign or send. The v0.1.27 [release notes](https://github.com/cjtsh/bitcoin-easy-multisig-signer/releases/tag/v0.1.27) make the same outdated claim. The default branch also trails the released branch. A third-party reviewer would regard this as a release-quality and trust problem, especially in a money-moving application.
- **Warm — The architecture is sensible but overburdened at the critical boundary.** One Python wallet engine, embit for descriptors/PSBTs, HWI for devices, and a small WebKit interface are reasonable choices. Centralized input selection, validated previous outputs, explicit network selection, local state, and tests are strengths. The single [`gui.py`](https://github.com/cjtsh/bitcoin-easy-multisig-signer/blob/e5e47a135fda09c8c91a87abccfd4d06b4941820/gui.py) handler owns HTTP, wallet sessions, prices, fees, device calls, finalization and broadcast. This makes transaction-state invariants harder to enforce and audit.
- **Warm — Concurrent API requests can invalidate a payment while an operation is in flight.** `_sign` rechecks the preparation ID after HWI returns, which is good. [`_broadcast`](https://github.com/cjtsh/bitcoin-easy-multisig-signer/blob/e5e47a135fda09c8c91a87abccfd4d06b4941820/gui.py#L526-L565) copies the prepared PSBT and then sends after releasing the state lock, without rechecking the preparation ID or scan generation immediately before submission. A refresh, import, or settings change in another request can invalidate the on-screen review during that gap. The currently enabled network is Testnet4; this race must be closed before mainnet broadcast.
- **Nice to have — Scanning is bounded but chatty.** [`scan_wallet`](https://github.com/cjtsh/bitcoin-easy-multisig-signer/blob/e5e47a135fda09c8c91a87abccfd4d06b4941820/wallet_service.py#L371-L454) requests up to 100 receive and 100 change addresses, with only two concurrent workers. That is comprehensible and safe for a small recovery wallet, but can be slow and reveal address clusters to a public explorer.

### Recommendations to fix

- **Hot:** Make `main` and the latest release point at the same audited source. Rewrite README, on-screen instructions, release notes and disclaimer so every statement matches v0.1.27's actual capabilities. Publish a new version for corrected artifacts; do not replace existing release bytes.
- **Warm:** Move prepared-transaction state into a small immutable object containing wallet/network, selected UTXOs, verified prevouts, outputs, fee, change descriptor, review ID and scan generation. Make sign/finalize/broadcast transitions validate that object. Hold a per-payment lock or atomically mark it as “broadcasting” immediately before the network request, then clear it only on a definitive outcome.
- **Nice to have:** Add a compact architecture/threat-model document and a supported BSMS/device matrix. Consider a local node backend and incremental scans for wallets with deeper history, while preserving clear coverage limits.

## 4. Grade

### Findings

- **Hot — Overall: 6/10 as an experimental tool; 3/10 for unattended mainnet use today.** The lower production grade reflects the unresolved change-path proof, incomplete final review, unverified signatures, build provenance, and lack of any mainnet rehearsal. It is not a judgment that the two Testnet4 sends failed; they are meaningful positive evidence.
- **Warm — Subscores:** design **7/10** (good use of established libraries and a small local architecture); implementation **6/10** (substantial guardrails, but critical invariants are incomplete); usability **5/10** (clear intended flow, but stale and contradictory instructions plus a weak final confirmation); test evidence **6/10** (135 passing tests and two documented hardware sends, with no mainnet or release-artifact audit repeated here).
- **Nice to have — Third-party impression:** A reviewer would likely call this a promising, unusually careful prototype, not a finished recovery product. The documentation drift and inferred change behavior would prevent a strong endorsement for real funds.

### Recommendations to fix

- **Hot:** Treat the mainnet broadcast gate as a release gate, not a version-number milestone: close all hot findings, perform a controlled mainnet dry run with independent transaction and device-screen checks, and obtain an independent security review.
- **Warm:** Define a supported wallet/export/device matrix and require a passing, reproducible test for each supported combination; label every other combination unsupported. Use a full local-node or Bitcoin Core transaction acceptance check for the release candidate.
- **Nice to have:** Re-grade after the fixes and a signed/notarized release are independently reproduced. An 8/10 would be plausible if the security boundary, user review, and distribution evidence are all strong.

## 5. Improvements and Phase 5 sequence

### Findings

- **Hot — Phase 5 must remain staged.** The code intentionally refuses mainnet broadcast ([`_broadcast`](https://github.com/cjtsh/bitcoin-easy-multisig-signer/blob/e5e47a135fda09c8c91a87abccfd4d06b4941820/gui.py#L526-L536)); no code change is needed to prepare and sign a mainnet dry run, but signed bytes can be broadcast by anyone who obtains them. The current handoff's X/Y/Z ordering is sound, provided the hot audit findings are addressed before the deliberate switch.
- **Warm — Reproduction evidence is uneven.** Tests cover the happy signing flow and a changed txid, but not malformed signatures, mutated PSBT metadata, a change branch unknown to the originating wallet, or concurrent broadcast invalidation ([signing tests](https://github.com/cjtsh/bitcoin-easy-multisig-signer/blob/e5e47a135fda09c8c91a87abccfd4d06b4941820/tests/test_signing.py), [send-flow tests](https://github.com/cjtsh/bitcoin-easy-multisig-signer/blob/e5e47a135fda09c8c91a87abccfd4d06b4941820/tests/test_send_flow.py)).
- **Nice to have — Recovery operations need a practical guide.** The target user is a nontechnical family member or professional. The app needs concise instructions for signer compatibility, confirming change, an unconfirmed transaction, fee bumping, and what to do when the broadcaster returns an unknown outcome.

### Recommendations to fix

- **Hot, first:** Correct the final review and change-path policy; bind signer output to the prepared PSBT and verify final signatures/prevouts/fees. Add regression tests for each. Only then rehearse mainnet with a small self-owned destination, two devices, no broadcast, and an independent Bitcoin Core decode and script verification. Keep the resulting signed bytes private and transient.
- **Hot, second:** Only after the owner explicitly authorizes a specific real send, add a mainnet-only, per-transaction opt-in that names the network and displays all final outputs and fees. Keep the existing default refusal. Test refusal, cancellation, stale state, duplicate submission, server timeout and unknown outcome. Independently verify the first confirmed mainnet payment and its change.
- **Warm:** Make reproducible release builds with enforced dependency/library integrity, Developer ID signing and notarization, a clear release checklist, and corrected documentation. Resolve the 25 sat/vB cap and fee-bump policy before a real-money release.
- **Nice to have:** Provide a one-page operator guide, a wallet/device support table, and a recovery path for stalled transactions. Reassess after real Mac, signer and node results are recorded without publishing wallet data.
