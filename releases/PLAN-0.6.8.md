## 1. What is actually wrong (in plain terms)

The app is not the problem. The problem is **the machinery that decides what
gets built, signed and published** — and more precisely, the *evidence* that
the machinery works:

1. **A door in the control room.** One workflow input (`candidate_run_id`) is
   pasted into a shell script by GitHub *before* the shell reads it, so the
   line that is supposed to validate it is itself the line that executes it
   (`CT-72`).
2. **A guard that cannot see half the building.** The script that enforces
   "only `main` may publish" hashes through *branch* names only, and only
   recognises two ways of publishing. Historical *tags* still carry
   publish-capable workflow text, and three other ways of publishing a release
   exist (`CT-76`, `CT-77`).
3. **A lock that covers two of 115 doors.** The source-mode check that is
   supposed to refuse a substituted hardware-wallet library hashes two files
   out of the 115 in the installed package, and the test that is supposed to
   prove it works asserts the constant rather than the package (`CT-73`,
   `CT-95`).
4. **Alarms wired to the label, not the switch.** Several release guards are
   "pinned" by tests that check the guard's *words* are present. Break the
   guard's *logic* — invert a comparison, append `|| true`, make a condition
   impossible — and all 55 workflow tests still pass (`CT-74`, `CT-75`).
5. **Two switches nobody ever flips.** The Bitcoin network constants and the
   bare-`/*` change-branch rule are correct in the shipped code, but no test
   fails if someone changes them to a wrong value (`CT-78`, `CT-79`).

Every one of those is **a check whose claimed coverage is wider than what it
actually does**. That is the family. Fixing the five instances without fixing
the family is what produced this cycle.

## 2. The governing principle: a control must be *closed under change*

The owner's requirement — add a menu, add a hardware wallet, ship 0.6.9, and
not re-learn this lesson — has one technical shape:

> **A control must cover a set that is derived from the artifact it protects,
> and it must fail when that set changes.**

Concretely, for every control in this repository:

| Question | Required answer | What it prevents |
| --- | --- | --- |
| What does it cover? | The actual shipped artifact set, enumerated | "2 of 115" |
| How is that set obtained? | Generated at build time from the artifact; stored as data | hand-written lists that drift |
| What happens when the set changes? | The build fails, naming the added/removed/changed member | 115 → 118 sailing through |
| What proves it? | A test that runs on real bytes and is *demonstrated failing* first | string pins over logic |
| What is out of scope? | A named, dated next-cycle list | unbounded re-litigation |

Applied to the three structural cases the owner named:

- **Add a hardware wallet** (upstream adds files to `hwilib`): the manifest is
  regenerated by the build and the stale-manifest check fails until it is
  updated — the three new files cannot be silently unchecked (§4, W3).
- **Add a feature or a menu** (new app code, no pipeline change): untouched
  controls stay valid; only the new behaviour needs its own tests.
- **Cut a new release** (0.6.9, 0.7.0): `version.py` is the single source, the
  release chain regenerates every artifact-derived manifest, and the control
  inventory (§4, M4) is checked against the code, not against prose.

## 3. Why 0.6.8, and what "fixed" will mean

- `AGENTS.md:36` forbids rebuilding a published version; a correction bumps
  `version.py`. v0.6.7 stays exactly as it is, signed and notarized, and the
  BLOCKED grade stays on the record attached to it. 0.6.8 is the release that
  answers it.
- **Fixed means:** the defect is closed by a test that has been demonstrated
  able to fail, the demonstration is recorded in
  [`PATCH-0.6.8.md`](PATCH-0.6.8.md), and the control's claim in the code,
  docs and release process matches what it actually does.
- **Fixed does not mean:** the grade is argued down, the ledger is rewritten,
  or a finding is closed because the panel is unlikely to look there.

## 4. Structural mechanisms (do these; the instances then mostly fall out)

These are the "solid base". Each is small on its own; together they are what
makes the next cycle's findings stop being re-discoveries.

**M1 — Workflow behaviour harness.** A test helper that *renders* a workflow
step the way the runner does (substituting `${{ }}` from a supplied context),
puts stub `gh`, `jq`, `shasum`, `git`, `gpg` and `docker` on `PATH` that record
argv and return scripted results, runs the step under `bash -e`, and asserts
on **outcomes** (exit status, which stubs were called with which arguments,
which files were written). Every release guard gets a row in a case matrix,
including the candidate-pass and candidate-tampered halves. This is the style
`PublishPathSweepTests` already uses with fixture repositories
(`tests/test_workflow_config.py:588`) — extended from "does the sweep script
reject this ref" to "does this guard refuse this input".
*Closed under change:* a new guard step with no case is caught by M4, not by a
reviewer's memory.

**M2 — Inputs are code.** No `${{ … }}` expression may appear inside any
`run:` body anywhere in `.github/workflows/`. Values arrive through `env:`.
Enforced by a lint over every workflow file, so the class is dead rather than
the instance.
*Closed under change:* a new step that interpolates fails the suite.

**M3 — Coverage is generated from the artifact.** Manifests (hwilib payload,
vendored tarballs, published assets, per-runner toolchain) are produced by a
build-time generator from the real artifact, committed for review, shipped in
the bundle, and re-checked in CI against a fresh installation. A generator
whose output no longer matches fails the build with the delta.
*Closed under change:* the 115→118 case fails the build by construction.

**M4 — A control inventory that can be checked.** `CONTROLS.md` lists every
security control: the claim it makes, the file and line that makes it, and the
test that proves it. A test parses the table and fails if a named test or file
does not exist, or if a control's code carries a claim comment with no entry.
This is the mechanical answer to the auditor's coaching theme "claims wider
than checks" (`probe.py:317` is the worked example).
*Closed under change:* a new "this is safe because…" comment with no control
row is a suite failure.

**M5 — One publish path, allowlisted.** The sweep (`check-publish-paths.sh`)
is inverted from a denylist of two patterns to an **allowlist**: the only ref
permitted to contain any workflow file that mentions release publication is
`main`, and on `main` only `build-candidate.yml` may. All refs are fetched —
heads **and tags**. Unreadable = offender. Fixture tests cover every form the
audit demonstrated (`write-all`, REST `gh api`, `curl`, `*-action-gh-release`,
`actions/create-release`).

**M6 — Evidence survives the session.** Every closing row in
`PATCH-0.6.8.md` cites a committed test or script; no `/tmp`-only reproducer,
no evidence that lives in one machine's shell history. Where a reproducer is
not naturally a test, it is committed under `tests/reproducers/`. This is the
answer to CT-48's "evidence no longer retrievable".

**M7 — Platform state is recorded and re-checkable.** Environments (with
their branch policies, required reviewers and secret *names*), rulesets,
Actions permissions, and workflow registrations live partly outside git. They
are recorded in `RELEASE-PROCESS.md` §5 and re-read by a script that diffs the
live platform against the recorded file, so a later auditor can re-derive the
half that git cannot show.

## 6. Order of work and discipline

1. **W1 + M2** — the injection and the class it belongs to.
2. **M1** (harness) — needed to prove W2, W4 and W10 honestly.
3. **W2**, then **W4** — the sweep and the string pins, each with its matrix.
4. **W3 + W21** — the whole-package manifest, with the stale-manifest build gate.
5. **W5, W6** — the two missing tripwires.
6. **W7 + M7** — credential wiring landed in a tagged revision, platform state recorded.
7. **W8–W14** — the remaining Low/Medium items, one commit each.
8. **W15–W20, W17** — vendor pins, source-mode lock, archive completeness, attestation note.
9. **M4** — the control inventory, written last so it reflects what actually landed.
10. **Ledger and release** — `releases/PATCH-0.6.8.md`, version bump, candidate → promote.

**Discipline rules for every item.**

- One item per commit; the commit message names the CT id.
- The test is written and **watched failing** before the fix; the observed
  failure is pasted into the `PATCH-0.6.8.md` row.
- No item closes by argument, by comment, or by "the panel probably won't".
- An adjacent "what if" discovered while fixing is written on the next-cycle
  list and **not** chased. That rule is what ends the loop the owner stopped.
- Nothing is published from this release until every Tier 1 and Tier 2 item is
  closed.
