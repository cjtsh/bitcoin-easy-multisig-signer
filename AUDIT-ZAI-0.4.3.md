# Bitcoin Easier Signer — complete code audit (v0.4.3, Phase 5 entry)

**Audit target:** `cjtsh/bitcoin-easy-multisig-signer`, branch `main` at `e8472a2` (source version 0.4.3, published release v0.4.3 built from `e7f97ac`). Audited 29 September 2026 by an independent reviewer (zai/GLM-5.3). I read every Markdown record (README, ROADMAP, PHASE-HANDOFF, PROJECT-HISTORY, AGENTS, DISCLAIMER, CHANGE-ADDRESS-REVIEW, SECURITY-REVIEW-0.2.0, AUDIT-BASELINE-0.1.27, all PATCH and PLAN records), every Python module (`wallet_service.py`, `signing.py`, `probe.py`, `gui.py`, `safe_http.py`, `network_config.py`, `network_settings.py`, `desktop.py`, `scripts/hwi_entry.py`), the `ui.html` interface, the CI workflow, both build scripts, both dependency locks, and the test suite. I installed the hash-locked dependencies in a clean Python 3.12 environment and ran the suite myself: **172 tests pass, 8 platform-dependent skips** (~38 s). I scanned all 121 commits of git history for wallet material and credentials: none found (only synthetic test fixtures and documentation references). I did not run a physical hardware signer, inspect the owner's wallet files, validate a downloaded DMG, or make any transaction.

**Assessment in one paragraph:** This is a credible, unusually careful recovery tool whose transaction engine is correct within its declared scope, whose key handling has no app-level exfiltration path, and whose engineering discipline (evidence records, fail-closed boundaries, adversarial tests, supply-chain hygiene) is well above what a third-party reviewer expects at this scale. The two prior audit rounds' hot findings (change-path trust, final-review screen, signature verification, signer-response binding, broadcast race) are each verifiably fixed in code and covered by regression tests. What keeps it from production today is not a discovered defect but unfinished Phase 5 gates: no mainnet dry run yet, no notarized distribution, an unresolved busy-memppool fee policy, and an inferred-BIP48-change trust decision that must be independently confirmed against the live wallet before real funds move.

## 1. Safety of operation — can this tool construct a bad transaction and lose Bitcoin?

### Findings

- **Hot — none found in the supported scope.** I attempted to break the transaction pipeline and could not find a path to a malformed, mis-valued, or mis-directed transaction that passes the code's own gates. The construction chain is sound end to end:
  - **Inputs are real and owned.** Every selected UTXO's full previous transaction is fetched and parsed; the builder requires `previous.txid() == utxo.txid`, `prevout.value == utxo.value`, and `prevout.script_pubkey == derived wallet script` before the input enters the PSBT (`wallet_service.py:809-821`). An explorer cannot fabricate a spendable output.
  - **Fees are exact by construction and conservatively sized.** The vbyte estimate assumes 73-byte signatures (the maximum) and is the single source of truth for both preview and builder (`_estimated_signed_vbytes`, `wallet_service.py:575-592`; `_select_inputs`, `595-626`); the build aborts unless `packet.fee() == fee` (`wallet_service.py:836-837`). The project's own independent measurement (305 vB actual vs 307 estimated; effective 5.033 vs requested 5 sat/vB) confirms the direction is conservative.
  - **Change cannot be under-dust and cannot silently vanish.** Partial sends require `total ≥ amount + fee + 546 sats` before building, so change is always ≥ dust (`wallet_service.py:770-771`); Send All requires the selected total to equal the scanned confirmed balance and produces exactly one output (`wallet_service.py:760-769`).
  - **The reviewed transaction is the broadcast transaction.** SegWit txid is computed before signing and re-verified at finalization (`signing.py:254-258`); every finalized output, the change address, the amount, and the exact fee are compared field-by-field against the immutable reviewed snapshot (`gui.py:777-790` `_check_final_review`); broadcast additionally requires a fresh outpoint-unspent check and a user-confirmed txid equality (`gui.py:804-831`).
  - **Malformed signatures cannot become a "complete" payment.** Every counted signature is DER-parsed, SIGHASH_ALL-only, and ECDSA-verified against the BIP143 digest of *this* transaction with the verified prevout value and witness script (`signing.py:75-114`). Corrupted-signature, wrong-key, wrong-sighash, and script/prevout-mismatch cases all raise.
  - **Sequence signals RBF** (`0xFFFFFFFD`, `wallet_service.py:796-798`), so a stuck payment is at least replaceable elsewhere — with the honest caveat that this app itself has no bump flow.
- **Warm — inferred BIP48 change for `No path restrictions` BSMS files.** For a Nunchuk-style export, change goes to `/1/*` derived from the same three xpubs under a strict guard (sorted 2-of-3 native-SegWit, identical four-level BIP48 origins, first receive address anchored; `wallet_service.py:318-334`). If the *source* wallet actually used custom branch indices, the change output lands on addresses the source wallet will not auto-discover. This is not loss — the same three seeds can always spend it via a descriptor import — but for a non-technical recovery operator it is effectively "funds the tool put somewhere the tool can no longer see," which is the failure mode this project exists to prevent. The code mitigates well (fail-closed scope, "standard-derived" labelling, review-screen and on-device verification prompts, the 0.4.3 bare-`/*` fail-closed fix, and the Sparrow/Nunchuk same-wallet equivalence proof in `CHANGE-ADDRESS-REVIEW.md`), and the residual risk is documented. It remains the single most consequential *trust* decision in the product, and it has never been exercised on the live mainnet wallet.
- **Warm — explorer dependence is structural but bounded.** Balances, UTXO sets, fee quotes, and broadcast all depend on public Esplora instances. The design accepts this with mitigations I verified: genesis and (for Mutinynet) block-1 checkpoint pinning (`network_settings.py:108-135`), strict schema validation with size caps (`wallet_service.py:111-158`), UTXO/totals consistency reconciliation (`wallet_service.py:458-473`), unspent re-checks immediately before prepare *and* broadcast — dual-source with tip-height agreement (≤2 blocks) on mainnet, single-source on practice networks (`gui.py:209-231`). Realistic worst cases are a refused or rejected payment, not a bad one: a lying explorer cannot forge the previous-transaction/script ownership check, and a stale-index double-spend is caught pre-submit or rejected by the network. Practice networks having only a same-operator recheck is a stated limitation, not an oversight.
- **Warm — fee policy creates liveness risk under stress.** Preparation hard-requires a live fee quote (mempool.space for mainnet/Testnet4; Mutinynet Esplora otherwise); an outage blocks recovery entirely (fail-closed, `gui.py:942-950`). The 1–25 sat/vB band and the 10,000-sat fee ceiling refuse exactly when a busy mempool demands more (`gui.py:959-963`). For an estate-recovery tool whose whole point is availability at an unpredictable future date, this is the operational weak spot. It is documented as the open Phase 5 fee decision; it is unresolved.
- **Warm — "Send All" means "all found by this scan."** The 20-address gap / 100-index scan cap is honestly labelled everywhere, but a non-technical operator who sends all may still believe the wallet is emptied while coins beyond the gap remain. Not a loss; a comprehension risk the UI mostly but not completely neutralizes.
- **Nice to have — preview/builder cap asymmetry.** `estimate_fee_preview` enforces the 10,000-sat ceiling only for Send All; a partial-send preview can display a fee the builder will then refuse (`wallet_service.py:677-681` vs the unconditional `check_fee_safety` at `772`). Cosmetic inconsistency, safe direction.
- **Nice to have — effective rate drift.** Because the estimate assumes maximum-length signatures, the *effective* sat/vB of the finalized transaction is slightly above the requested rate when real signatures are shorter. The absolute fee is what was reviewed, the drift is ~1%, and it is disclosed at finalization (`effective_fee_rate`). Acceptable.
- **Nice to have — concurrent two-device signing refuses the second response** (`state.prepared is not payment` after the first atomic replace, `gui.py:735-738`). Fails safe; mildly confusing if an operator ever ran two signings in parallel (the UI serializes them).

### Recommendations to fix

- **Hot:** Before the first real-money partial send, independently establish the live wallet's change policy — derive the first *unused* change address and its full script/derivation in the originating wallet (or on a signer screen) and compare — exactly as `CHANGE-ADDRESS-REVIEW.md` and the Phase 5 gate already require. If it cannot be established, keep that wallet on the explicit Send All path or a declared-change export. Do not soften the strict-BIP48 guard; wallets outside it must stay fail-closed.
- **Hot:** Complete the Phase 5 mainnet dry run unchanged in code (prepare → two-device sign → finalize in memory → independent decode, witness-script, output, fee and txid verification → discard), and treat it as the release gate it is. The code already refuses mainnet broadcast (`gui.py:799-803`); keep it that way until the dry run passes and a separate, explicit per-transaction mainnet opt-in is designed and tested.
- **Warm:** Resolve the fee decision deliberately before mainnet: either a bounded high-fee override behind a fresh, explicit high-fee review (with a stubbed busy-memppool quote test), or a plain-language referral to an established wallet when the cap binds. Extend the same thinking to a minimal RBF-bump runbook, since inputs already signal replaceability.
- **Warm:** Add a second, independently operated outpoint source for Testnet4/Mutinynet (or a user-run node option), and consider a `testmempoolaccept`-style acceptance pre-check against a node before presenting broadcast as ready. Mainnet's dual-source check is good; make practice networks match as soon as a reliable second service exists.
- **Warm:** Define a fee-outage policy for urgent recovery (e.g., allow a manually entered rate with an explicit "no live reference" acknowledgement), so a third-party API outage cannot lock a time-sensitive estate recovery out of the tool.
- **Nice to have:** Apply the 10,000-sat ceiling inside `estimate_fee_preview` for partial sends so the preview can never show a fee the builder refuses.
- **Nice to have:** Surface an explicit "the scan stops looking after 20 unused addresses; Send All empties only what was found" acknowledgement on the Send All review, not just in the warning text.

## 2. Safety of code & keys — could keys be stolen or the signing process subverted?

### Findings

- **Hot — none. There is no seed, PIN, or private-key path anywhere in the codebase.** I verified every input surface: the BSMS parser rejects private keys outright (`probe.py:157`), HWI is the only device channel, and the app's interface to it is a no-shell subprocess with the signing PSBT passed on **stdin**, never argv (`probe.py:234-289`; the 0.3.0 stdin change is exactly right), with bounded timeouts (180 s discovery/xpub, 600 s signing) and no automatic retries. Keys cannot be stolen *by this app* because it never possesses them; the true signing boundary is the device screen, and the code reinforces rather than fights that.
- **Hot-grade positive — the signer-response boundary is exemplary.** `accept_signature_update` (`signing.py:117-145`) clones the app's own reviewed PSBT, imports **only** partial signatures from the device response, requires the unsigned transaction bytes to be identical, requires prior signatures to survive, then cryptographically verifies everything. Device-returned global/input/output metadata — the classic channel for a malicious "signer" to rewrite a payment — is structurally incapable of entering prepared state. The 0.4.0 Jade incident (over-strict byte comparison rejecting reordered fields) and its 0.4.1 fix (verify-what-matters instead of compare-everything) show this boundary was hardened against *real* device behavior, and the regression tests cover reordered fields, added metadata, swapped transactions, invalid signatures, and removed prior signatures.
- **Warm — the local API trust boundary is "same user on this machine," and it is well defended at that boundary.** Loopback-only bind on an ephemeral port, Host-header check, Origin check on writes, token in the URL fragment (never in a response body or referrer), `hmac.compare_digest` comparison, no request logging, `no-store`/`nosniff`/`no-referrer`/CSP headers (`gui.py:426-497`). The UI builds every DOM node with `createElement`/`textContent` — I found **zero** `innerHTML`/`eval`/`new Function` sinks in `ui.html`, so wallet-derived strings (descriptors, addresses, HWI error text) have no script-injection surface. Residual: any code already running as the same user could talk to HWI itself; that is inherent to desktop signing and correctly documented as accepted.
- **Warm — CSP retains `'unsafe-inline'` for scripts** (`gui.py:413-418`) because `ui.html` carries inline JavaScript. With no injection sinks it is defense-in-depth that is missing rather than an exploitable hole, but a money-adjacent local app should not need it.
- **Warm — privacy of public wallet data is handled with unusual care.** Only derived addresses and public txids leave the machine, only to the configured explorer, only after explicit consent; xpubs never appear in any explorer request. Diagnostics are fixed-code/timestamp only (`gui.py:56-64, 323-353`); PSBT saves are `O_EXCL`, mode 0600, never overwriting (`gui.py:296-316`). Outbound HTTP refuses all redirects and keeps TLS verification on with the *bundled, pinned* certifi store — the trust-store regression post-mortem and its CI re-check with poisoned `SSL_CERT_FILE` is exactly how that class of bug should be prevented (`safe_http.py`, `desktop.py:86-105`).
- **Warm — supply-chain posture is strong for the artifact, incomplete for the publisher.** Full dependency tree hash-locked (571 hashes in the desktop lock; the source lock's single hash is complete because `embit` is the only runtime dependency), `LIBUSB_SHA256` mandatory in CI with the build aborting when unset, CycloneDX SBOM per release, all GitHub Actions pinned to commit SHAs, workflow manual-dispatch only, immutable one-version-per-build releases, `codesign` without `--deep` with strict verification. The gap: the DMG is still ad-hoc signed and unnotarized (blocked on Apple Developer enrollment), so a recipient cannot cryptographically attribute the artifact to you — `SHA256SUMS` published in the same channel detects transfer corruption, not publisher impersonation. Known, held, and correctly listed as a Phase 5 dependency.
- **Warm — the signing TCB is inherited, not audited.** embit 0.8.0, HWI 3.2.0, pywebview, PyInstaller, libusb are all reasonable, canonical, pin-and-hash-verified choices — but nobody in this project's records has audited embit's PSBT/ECDSA internals or HWI's device transports, and a build-time compromise of any of them defeats every app-level safeguard. This is the standard residual risk of "off-the-shelf, not from scratch," stated here because the tool's own documents already state it honestly.
- **Nice to have — a signed, unbroadcast mainnet transaction is itself spend authority.** During the dry run, finalized bytes live in process memory (and can be saved deliberately). The plan's guidance (tiny self-owned amount, short-lived session, keep bytes private, treat them as sensitive) is correct; Python cannot guarantee memory erasure.

### Recommendations to fix

- **Hot:** Complete Developer ID signing and notarization (with the reverse-DNS `CFBundleIdentifier`) before the DMG is placed in front of the spouse/lawyer/accountant it is meant for. Until then, keep the README's right-click→Open instruction and the UNSIGNED-TEST artifact naming so nobody mistakes the current build for a verified publisher release.
- **Warm:** Externalize the inline JavaScript into a bundled `.js` file served by the local server and tighten CSP to drop `'unsafe-inline'` for `script-src` (a per-session nonce is even better). Pure hardening; no behavior change.
- **Warm:** Document the supported device/firmware matrix actually exercised (Jade, Trezor Safe 3, Ledger Nano S Plus on the recorded versions), and record HWI 3.2.0's supported-model list as a reviewed reference, so a future device-family addition is a decision rather than an accident.
- **Nice to have:** For the mainnet dry run, add a one-click "clear signed transaction from this session" control so the finalized bytes' lifetime in app state is operator-visible and deliberately ended.
- **Nice to have:** When Python/HWI are upgraded, regenerate both lock files and re-pin actions in the same change, as AGENTS.md already requires — add a scheduled reminder (e.g., quarterly dependency review) so the pins do not silently age.

## 3. Efficiency of design — is this best of breed? What would a third party say?

### Findings

- **Hot — verdict: a third-party reviewer would rate this a genuinely impressive, purpose-built tool — "wow," with reservations about doc sprawl and unfinished distribution.** The reservations a hostile reviewer would raise are the held Phase 5 items (no notarization, no mainnet evidence), not the engineering. Specifically impressive:
  - **One engine, three networks, no forks.** `wallet_service.py` + `signing.py` serve Testnet4, Mutinynet, and mainnet behind a data-only network profile (`network_config.py`); there is no network-specific transaction code path to drift. The architecture rule is stated, enforced, and tested.
  - **State-machine discipline around the payment.** The frozen `PreparedPayment` (wallet identity, chain, scan generation, review ID, txid, review values, selected outpoints) binds every sign/finalize/broadcast transition; staleness is detected by generation and object identity; broadcast holds the session lock through submission so no concurrent refresh/import/settings change can alter an in-flight payment (`gui.py:234-268, 692-704, 813-816`). The stale-screen bug class from 0.2.1 has a DOM regression test pinning it shut.
  - **The off-the-shelf selection is correct, not lazy.** embit (small, purpose-built descriptors/PSBT library), Bitcoin Core HWI (the reference device implementation), Esplora's standard API, pywebview + PyInstaller for a native Mac shell, stdlib `http.server` for the loopback API. No framework, no blockchain-as-a-service, no key-handling code written here. Every component earns its place and the boundaries between them are explicit.
  - **Documentation as an engineering artifact.** Phase records with acceptance gates, per-release evidence files with run URLs and SHA-256s, honest separation of owner-reported vs independently verified evidence, superseded statements marked rather than deleted, and an agent guide whose invariants match the code (I checked; they do). The post-mortems (trust-store regression, 0.2.0 field-order rejection, Jade PIN wait) read like a team that treats failures as specifications for tests.
  - **Test quality is adversarial, not decorative.** 172 tests covering corrupted signatures, metadata-rewrite attacks, txid swaps, unknown-outcome broadcast locks, concurrent import during broadcast, spent-outpoint refusal, mainnet refusal, plus Node UI state regressions; CI re-runs the suite on the extracted source archive. I ran the suite myself in a clean environment: green.
- **Warm — `gui.py` concentrates too much.** HTTP plumbing, session state, fee/price fetching, settings, and the prepare/sign/finalize/broadcast orchestration live in one 1,057-line file. It is organized and guarded, but the payment lifecycle is the security-critical core and deserves its own module so its invariants can be read (and reviewed) in isolation.
- **Warm — documentation volume has become a navigation problem.** Ten-plus overlapping history files, with correction notices stacked atop the README. Each individual document is good; the *set* has redundancy and drift risk that currently survives only because of disciplined editing. A third party's second-most-likely criticism after "not notarized" is "I can't tell which document is current."
- **Nice to have — scanning is slow and chatty by design.** Up to ~200 address queries per scan with 2 workers, sequential 10-address chunks (`wallet_service.py:492-507`). Bounded, consented, and honest — but a wallet with deep history will feel sluggish, and every scanned address is disclosed to the explorer.
- **Nice to have — `ui.html` at ~1,500 lines mixes structure, styling, and logic.** With inline JS and inline CSS in one file, the CSP tightening above and any future UI work would both benefit from splitting assets.

### Recommendations to fix

- **Hot:** Keep the one-engine rule absolute through Phase 5 — resist any pressure to add a "mainnet-special" path, endpoint, or flag beyond the deliberate per-transaction broadcast opt-in already specified in the roadmap.
- **Warm:** Extract the payment lifecycle (PreparedPayment transitions, sign/finalize/broadcast gating) from `gui.py` into its own module with the invariants as docstrings and a dedicated test file; leave `gui.py` as HTTP/session plumbing. This is the highest-leverage refactor for third-party reviewability.
- **Warm:** Consolidate the document set: one short CURRENT-STATUS page (version, what's proven, what's next, links), README trimmed to capabilities + install, and move the per-release correction history into a single CHANGELOG-style file. Mark the rest archive.
- **Nice to have:** Increase scan parallelism modestly (e.g., 4–8 workers) with the same gap logic, and show per-branch progress; consider incremental re-scans from the last used index within a session.
- **Nice to have:** Split `ui.html` into HTML/CSS/JS assets (also unblocks the CSP fix), and add a plain-language architecture/threat-model page — half of it can be lifted from AGENTS.md's invariants, which are already excellent.

## 4. Grade

### Findings

- **Overall: 8/10 as a practice-network multisig recovery tool and mainnet-dry-run candidate.** On the prior audit's own bar ("an 8/10 would be plausible if the security boundary, user review, and distribution evidence are all strong"), the security boundary and user review now clear that bar in code and on hardware, and distribution evidence is strong at the artifact level (hashes, SBOM, immutable releases) while publisher-level evidence (Developer ID/notarization) still waits on Apple enrollment. This is not grade inflation relative to 0.1.27's 6/10: every hot and most warm findings from that audit are fixed *and regression-tested*, and the fixes were validated by real device payments (0.3.2 Ledger+Trezor, Jade+Trezor; 0.4.1 Ledger+Jade confirmed on-chain).
- **For unattended mainnet use by the intended non-technical user today: 5/10.** Not because a defect would eat the funds — no such defect was found — but because the remaining gates exist precisely for that step and are not yet passed: no mainnet dry run, no change-policy verification against the live wallet, unresolved busy-memppool fee policy, and a DMG the target user must bypass Gatekeeper to open. Enabling mainnet broadcast before those close would be a process failure, not a code failure.
- **Subscores (out of 10):** design **9** — right architecture, right components, honest boundaries; implementation **8** — careful, tested, with the `gui.py` concentration and doc sprawl as the visible costs; usability **8** — plain-language gates, visible reasons, the final screen shows everything that matters, with the operator guide and scan-speed still open; testing & evidence **8** — adversarial suite plus recorded physical evidence, with practice-net single-source checks and no independent audit of embit/HWI internals; distribution/readiness **5** — hash-verified but unsigned/unnotarized, mainnet untested.
- **Third-party impression:** "This thing is careful" — the expected reviewer quote is that the guardrails (signature-only import, verified prevouts, outcome-unknown handling, fail-closed parsing) are what a from-scratch production wallet should have and often doesn't, and that the project's own documentation of limits does more for trust than most audits.

### Recommendations to fix

- **Hot:** Treat the Phase 5 sequence as the grading rubric it already is: (1) live-wallet change-policy verification, (2) mainnet dry run with independent decode, (3) fee-policy decision, (4) notarized build — then, only on explicit owner authorization, the deliberate mainnet opt-in behind per-transaction confirmation. Each closed gate moves the mainnet score; nothing else will.
- **Warm:** Commission at least one external review of the two inherited critical components (embit's PSBT/ECDSA paths; HWI's transport) or pin them to releases that have one, and record the provenance decision in the repo.
- **Nice to have:** Re-grade after the dry run and notarized release; a 9/10 as a scoped 2-of-3 recovery tool is a realistic ceiling, with the remaining point reserved for practice-network independence checks, the operator guide, and the passage of time with no incidents.

## 5. Improvements

### Findings

- **Hot — Phase 5 is correctly sequenced; the risk is skipping steps, not missing ones.** The code needs no change for the dry run (only `_broadcast` refuses mainnet, `gui.py:799-803`), which is itself evidence the gate was designed rather than bolted on. The improvements that matter most are therefore procedural, in order: change-policy proof for the live wallet, dry run with independent verification, fee decision, notarization, then the explicit opt-in.
- **Warm — operator-facing deliverables lag the engine.** The plain-language one-page guide (devices, test payment, what a missing device looks like, "not finished until confirmed," what to do when stuck) is planned but not written; for the tool's actual user it is as important as any code gate.
- **Warm — the stuck-payment story is thin.** RBF is signaled but there is no bump flow and the guidance points back to the originating wallet; a fee-bump runbook (or a minimal bounded bump feature) belongs on the Phase 5 list.
- **Warm — dependency freshness.** HWI 3.2.0 caps Python below 3.13 and pins the device-support surface to mid-2025-era firmware; embit 0.8.0 likewise. Fine today; a deliberate upgrade review should be scheduled rather than discovered.
- **Nice to have — product surface:** fee-preview cap parity, second-source practice-net checks, scan speed/progress, doc consolidation, asset split, device/firmware matrix page, session "clear signed bytes" control, quarterly dependency/pin review.

### Recommendations to fix

- **Hot, first:** Verify the live wallet's change policy independently before any partial mainnet send (first unused change address + full script/derivation confirmed in the originating wallet or on a signer screen). Record the proof's *shape only* in the repo, per the standing no-wallet-data rule.
- **Hot, second:** Run the Phase 5 dry run exactly as gated, verify the finalized transaction independently (decode, per-input witness vs the wallet's own witness script, outputs/change/fee vs the review, txid before = txid after), keep the bytes private, and do not broadcast. Then make the fee decision (bounded high-fee override with fresh explicit review, or documented referral) and land Developer ID + notarization with a reverse-DNS bundle identifier.
- **Hot, third:** Only on explicit owner instruction, implement the mainnet broadcast opt-in as specified: per-transaction, visible, naming mainnet, default-refused, txid-bound, with tests proving broadcast remains impossible without it — including cancellation, stale-state, duplicate-submission, timeout and unknown-outcome paths.
- **Warm:** Write the one-page operator guide and a stuck-payment runbook; add the supported wallet/export/device/firmware matrix; schedule the quarterly dependency/pin review covering HWI, embit, certifi, actions pins, and the libusb digest.
- **Nice to have:** The remaining polish items — `gui.py` payment-lifecycle extraction, doc consolidation, `ui.html` asset split + strict CSP, faster/progressive scans, fee-preview cap parity, and a session control to clear signed bytes. None of these should delay the Phase 5 sequence; all of them make the tool read, to a third party, like what it already is: carefully built.
