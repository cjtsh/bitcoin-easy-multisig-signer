# Agent guide

## Read order

1. `CURRENT-STATUS.md` for current version, evidence and open gates.
2. `README.md` for current user-visible behavior and supported scope.
3. `PHASE-HANDOFF.md` for current status, version gates and owner test.
4. `RELEASE-HISTORY.md` for the version-by-version record; each entry links its full evidence file where one exists.
5. `CHANGE-ADDRESS-REVIEW.md` for the BSMS/change trust boundary and the mainnet change-policy gate.
6. `HWI-DEPENDENCY.md` before touching the Python version, the device list, or a dependency bump. HWI decides which devices work, which Python the app builds on, and when a rebuild is mandatory.
7. `RELEASE-PROCESS.md` before building a DMG or changing release controls. It is the agent-neutral build and promotion contract. `SIGNING.md` defines what each platform's download carries — signature and provenance — and the release-key policy; read it before touching any workflow or build script. `WINDOWS-PORT.md` carries the Windows CI portability rules and the retired standalone-fork history.
8. Current source and tests. `ROADMAP.md` and `PROJECT-HISTORY.md` preserve history and can describe older releases.

## Architecture

One engine serves Testnet4, Mutinynet and mainnet. `probe.py` parses BSMS and checks public hardware identities; `wallet_service.py` resolves wallet paths, scans via Esplora and builds PSBTs; `signing.py` binds and verifies HWI signing updates and finalizes native-SegWit multisig. `gui.py` owns loopback API/session state, fee/price references, signing and broadcast gates; `ui.html` is the shared interface; `desktop.py` wraps it in a Mac WebKit window. `network_config.py` is the network parameter switch. `safe_http.py` refuses redirects and keeps TLS verification on. Never create a separate transaction or signing engine for a network.

## Invariants

- No seed, PIN or private key input, wallet creation, silent signing, or unapproved mainnet broadcast.
- The owner requires a **single BSMS file** for spouse/lawyer/accountant recovery. Do not request a Nunchuk database or introduce a second-file workflow. The 0.3.2 fallback uses BIP48 `/0/*` receiving and `/1/*` change only for a native-SegWit sorted 2-of-3 wallet with all three matching four-level BIP48 account origins and a first receive address matching the file. Label change as **standard-derived**, never BSMS-declared. Nunchuk's BSMS writer omits custom branch indices, while its parser defaults an unspecified pair to `{0,1}`; a custom historical layout may therefore be lost in BSMS. Document this scope. Nonstandard wallets retain the explicit no-change Send All path. The same rule applies on every network.
- The current wallet-signing scope is any valid BSMS quorum with **two or three total keys**; the threshold always comes from the file. This includes 1-of-2, 2-of-2, 1-of-3, 2-of-3 and 3-of-3. Reject larger key sets. The inferred BIP48 change fallback above remains restricted to its exact standard 2-of-3 case; all other policies need an explicitly declared change path for partial sends or the deliberate Send All path.
- A bare `/*` matching the first address directly at `xpub/0` does not anchor the BIP48 `/0/0` receive path and must never enable inferred `/1/*` change. An explicit `/0/*,/1/*` restriction that conflicts with the first address is rejected. A BSMS first receive address never independently proves an absent custom change path; see `CHANGE-ADDRESS-REVIEW.md` before mainnet gate work.
- Never preselect Send All. Standard BIP48 wallets open with a custom amount available; unsupported change layouts explain why the amount is unavailable and require a deliberate Send All checkbox action before review. **Bitcoin mainnet is the opening network**, and 0.6.1 reaches every other network through the "Enter Developer Mode" gate on the opening screen; all networks remain selectable and no test-network support is deprecated. The selected network is in-memory for the session only and the app reopens on mainnet; the practice-network radio cards must never be visible outside developer mode, and the orange/green frame and the network badge must never be hidden or allowed to disagree. Live Bitcoin is never a radio card inside the gate: it is the network the gate returns to, and a request to select mainnet while the gate is open is refused, because that is the one state in which the frame and the badge would disagree.
- A PSBT input must match an independently fetched historical transaction and the wallet's derived script/value. A signer response may rewrite PSBT metadata, but none of that metadata may enter prepared payment state. `accept_signature_update` clones the reviewed PSBT, imports only partial signatures, and verifies each against the original transaction, script and verified prevouts. Different unsigned transaction bytes, input/output counts, removed prior signatures and invalid signatures are refused. Store and finalize the returned canonical clone, never the raw HWI response.
- HWI enumeration has a 180-second bound because Jade's enumeration performs PIN-server authentication and can require two slow on-device PIN entries; Each matched device public xpub verification also has 180 seconds, because the device may ask for further authorization. An explicitly requested signature has 600 seconds because Ledger may require two on-device review rounds. Keep the owner informed in the GUI while it waits. Never automatically retry a signing command after timeout or device-open failure.
- Before broadcast, verify every signature, witness/prevout, output, fee and txid against immutable reviewed state. The final screen must show the same fields. A concurrent request must not change the payment during submission.
- Treat public explorers and fee quotes as observations. Never call a gap-limited scan a complete wallet sweep. Never silently fall back to a different server.
- After an outgoing practice-network broadcast, keep a session-only transaction ID and pause another payment until the explorer reports one confirmation. Reimport of the same wallet within the session must retain the pending ID. An address scan's mempool spent total also pauses sends, including after a restart. A missing transaction status is not confirmation. Incoming pending funds alone do not pause confirmed outputs.
- A broadcast transport/malformed-response failure is outcome-unknown: clear the prepared payment and refuse a blind retry. Recheck confirmed funding and selected outpoints before preparation and broadcast. Mainnet uses an independently operated second Esplora for public outpoint IDs after the operator's disclosure consent; Testnet4 and Mutinynet currently have only a fresh same-explorer check. These checks reduce stale-index risk but cannot replace a trusted node's consensus view.
- The frozen `PreparedPayment` is the only prepared transaction state. Keep its wallet identity, selected chain, scan generation, review ID, txid, selected outpoints and review values bound through signing/finalization/broadcast. In `ui.html`, clear the old signer/final panels whenever a payment changes; the owner observed an old final transaction below a new unsigned review in the installed 0.2.1 app. `tests/ui_state_reuse.cjs` covers that transition.
- Version 0.4.0 refreshes the light UI and shows a session-only last-payment receipt after confirmation. The receipt stores only the public explorer URL in browser memory. It is not a payment-history database and disappears after a new wallet/network or app restart. The pending-payment banner remains the source of truth until one confirmation; visual changes must not bypass any review, signature or broadcast gate.
- Versions 0.3.0 and 0.3.1 blocked the owner's custom amount. With the published 0.3.2 release, the owner reports two successful Mutinynet payments using Ledger + Trezor and Jade + Trezor, the second without restarting the app. This is owner-reported physical acceptance; transaction IDs, diagnostics and on-device review details were not supplied. Do not attribute it to automated tests or extrapolate to mainnet.
- The owner reported an installed 0.4.1 Ledger + Jade Mutinynet payment. Its privacy-limited diagnostic report recorded two verified signer responses, verified finalization and accepted broadcast; Mutinynet's Esplora later reported the owner-supplied public transaction confirmed. The report omits device identities, so pairing comes from the owner's account. Do not commit the transaction ID, diagnostic file or any wallet material. Version 0.4.2 only lengthened Jade authorization during discovery; that wait change was not separately physically tested. The current 0.4.13 interface and signing gates have not had a reported physical transaction walkthrough.
- Mutinynet is a custom Signet and **shares genesis with ordinary Signet**. Always check its pinned block-1 hash as well. `tb1` and testnet BIP48 coin type do not distinguish it from Testnet4. Carry the explicit selected chain through scan/build/broadcast; never reuse Testnet4 coins or silently switch endpoints. Existing two-network settings files must keep their saved URLs.
- Do not commit or emit BSMS records, xpubs, addresses, PSBTs, raw transactions, settings, device paths, or real wallet/test artifacts. Diagnostic reports use only fixed codes, the selected network, a validated device **class** and timestamps. A device model is not an identity: no path, serial, fingerprint, address, error text or other free text may be written, and anything failing that token check is dropped rather than escaped. Rejections are attributed to a real stage via `DIAGNOSTIC_ROUTE_STAGES`; convenience routes (estimates, price, settings, status) record nothing, so chatter cannot crowd the 80-event buffer. A caller that passes `found` always gets the key — `signer_check` writes an explicit `[]` when no usable device was visible, because an absent key is indistinguishable from a field that is never written.
- Audit tripwires are part of the fix. A money-path or release-path change is not done until a test is demonstrated able to fail: break the control on a disposable copy, watch the named test go red, restore. Assert the specific refusal message and include the positive half. Pin published test vectors rather than re-calling the library under test. Pin what used to float (runner images, source-mode tool identity, action SHAs). When `version.py` moves, update `AGENTS.md`, release notes and every user-facing version reference in the same commit. Work the audit ledger; never close a finding by silence. `RELEASE-PROCESS.md` §5 holds the full rules.

## Development and release

These rules apply to every coding agent and tool. Follow `RELEASE-PROCESS.md`
for every candidate and public release. Build only through the checked-in script
or manually dispatched workflow. One dispatch-only pipeline,
`.github/workflows/build-candidate.yml`, builds macOS, Windows and Linux from
the same commit in the same run and is the only publish path; the retired
per-platform workflows must not return. A release uses a signed, notarized
`publish=false` candidate, then a `publish=true` dispatch from the same commit
with that candidate's run ID; the workflow verifies and publishes those exact
candidate bytes for every platform, signs the CI-generated `SHA256SUMS` with the
release GPG key (`SHA256SUMS.asc`), and attaches a Sigstore attestation to every
asset — see `SIGNING.md`. Local builds are fine for quick development checks but
are not release artifacts. Owner hardware acceptance is required when app
behavior changes. Manual publication is prohibited; if the workflow is
unavailable, wait to publish.
Do not skip the dependency, libusb, packaged-app, SBOM, checksum, notarization,
or applicable hardware acceptance gates.

Use Python 3.12 because bundled downstream dependency Bitcoin Core HWI 3.2.0 declares `Requires-Python >=3.9,<3.13`; Python 3.14 is outside that range. It is the only dependency that caps Python. **`HWI-DEPENDENCY.md` is the canonical record** of the pinned version, supported devices, rebuild triggers and cost of a bump; read it before changing any of them. The desktop build script rejects unsupported versions, both workflow jobs pin 3.12, and both hash lock files were generated for 3.12. Upgrade HWI, regenerate/test locks, and change all pins together before considering a newer Python. Run the full suite, JS syntax, `bash -n`, source archive tests and packaged Apple Silicon checks. Dependency locks are hash-verified. `LIBUSB_SHA256` is mandatory for the Mac build. Publish the CycloneDX `BUILD-SBOM.json` with the DMG and include it in `SHA256SUMS`. The GitHub workflow is manually dispatched; pushes alone must not publish. Never replace an existing release's assets. The source revision is **0.6.6**. The latest published release is **0.6.4** until the 0.6.6 candidate is promoted through the unified pipeline; never claim a published version the release page does not carry. 0.6.6 is the Color Team cycle-2 remediation: BIP-143 published vectors, money-path and HWI-identity pins, BIP-62 low-S, a key-proof before any PSBT is sent, a large-amount prompt a lying price cannot suppress, broadcast pre-checks outside the session lock, pinned runners and lock tooling, and release-channel hygiene. The dated AI-generated Z.ai v0.6.4 report assigns Green under its rubric after reviewing automated publication; this is evidence about one revision and stated coverage, not a certification or guarantee. No independent human end-to-end security review is recorded. The historical v0.6.3 report found no Critical or High issues and assigned Yellow because that release bypassed automated publish gates. Version 0.6.3 added signing-time device identity checks, a pinned embit parser update, and build/release hardening; its owner reported a successful Mutinynet payment with the released DMG. Version 0.6.2 retired the network of a finished review together with the review, so a broadcast cannot inherit an earlier payment's mainnet opt-in. Version 0.6.1 is the interface release whose transaction and signing engine is unchanged from 0.5.1: it opens on Bitcoin mainnet and reaches Mutinynet and Testnet4 only through the "Enter Developer Mode" gate, whose panel offers those two practice networks and never live Bitcoin. 0.4.15 was the signed/notarized OneKey owner-test candidate, and 0.5.0 was the unpublished mainnet-broadcast candidate whose engine 0.5.1 publishes. Its final screen carries **one** confirmation, which names real Bitcoin; the backend additionally requires a mainnet opt-in flag that `broadcast_transaction` defaults to `False`, so a caller that omits it fails closed. That is one operator checkbox, not two — the backend flag is defence in depth against a caller, not a second human action. Use a new patch version for corrections and update `version.py`, release notes and user-facing version references together.

Keep the nontechnical operator's screen simple. Make technical checks automatic and explain unsupported conditions in plain English. **Accept the input an operator naturally types rather than teaching them a format:** `btcToSats` normalises a leading bare `.` to `0.` and tolerates a trailing `.`, and `tidyAmount` rewrites the box into its canonical spelling on blur. A rejected amount must say what is actually wrong — decimal places, not-a-number, or genuinely below the 546-satoshi floor — never one message blaming the size for a spelling problem. **One progress bar, one owner:** `setBusy` returns a token-bearing handle (`say`/`done`) and only the newest holder may change or clear the bar, so overlapping operations — a balance check, a device search, signing, broadcast — can neither display each other's text nor clear each other's messages. A finished operation must never be able to disturb a running one. **One palette, and only roles:** colours may be named *only* inside the four token blocks in `ui.html` (light, dark, mainnet light, mainnet dark). Every other rule names a role — `--canvas`, `--ink`, `--accent`, `--pending`, `--done`, `--failed` and their relatives. Five hues fill fixed roles: neutral surfaces and text, one action colour, and pending/done/failed. Light and dark must define exactly the same roles, because a role missing from dark silently inherits the light value, and that is how a white border appears on a dark screen. Mainnet is those same roles read more loudly, never a second palette. `tests/test_palette.py` fails the build on a colour named outside those blocks, on a role missing from either theme, on a mainnet override of a role that does not exist, and on `--ink` falling below 7:1 against `--canvas` or `--paper`. This exists because colours drifted one revision at a time: by 0.4.12 there were 113 colour literals and 91 distinct values, of which only 10 had ever been chosen. **The theme is decoration and must never be able to break the app:** it runs in front of every other line, so it probes each browser API before use and the whole block is wrapped. The owner wants one Mac install and transaction walkthrough per milestone after extensive automation, not repeated manual tests for small revisions. Do not recommend 0.2.0 for signing: Jade and Ledger responses were rejected by its field-order check. A 0.2.1 Testnet4 broadcast had two verified signatures and confirmed. Do not claim 0.3.0 Mutinynet/device acceptance from automated tests alone; its owner walkthrough remains open. A 0.5.0-or-later build may submit a mainnet transaction only with the per-transaction final-screen consent and the backend opt-in; no build before 0.5.0 can submit one at all. Never remove either gate or submit as part of build/testing.
